# Threat model

Status: living; rewritten on 2026-11-17, after workspace trust (`decisions/0004-workspace-trust.md`), the effects-based permission policy (`decisions/0003-effects-based-permission-policy.md`) and the hardening of 2026-11-17 (tool input validation, script capabilities and limits, the Linux sandbox, language-server install consent, fenced MCP results); updated the same day for the owner's four decisions (capabilities for every kind of script, language-server installs asked in every mode, `sandbox.required` on by default on Linux and macOS, stdio MCP servers in the sandbox); updated again the same day for an independent audit (SEG-19 to SEG-22, and boundaries 1 and 6), and for a second independent audit (SEG-24 to SEG-34; SEG-8, SEG-9, SEG-19 and SEG-20 revised). Every row of "Known gaps" names the test that pins its current status; a row without one says so.

The product is written as "the app", its binary as `<command>`, its project folder as `.<command>/`.

## What the app is, for this purpose

A local process that runs with the user's privileges, takes instructions from a language model, and on those instructions reads and writes files, runs shell commands and makes network requests. It is single-user and local (`decisions/0008-single-user-local-product.md`). The barriers between the agent and the user's account are the permission policy (it decides whether a call may run, and who is asked), workspace trust (it decides what a folder may bring), the script runtime's own limits, and, where the system provides one, the write sandbox for shell commands. Nothing else confines the agent.

## Assets

| Asset | Where | Why it matters |
|---|---|---|
| Credentials vault | `secrets.json` in the data folder; its key in `secrets.key` beside it (0600, the default), or in the system keychain (`secrets.key` then only points there) when `<PREFIX>_SECRETS=keychain` is set; provider keys and tokens, MCP OAuth tokens, the Cloudflare sign-in of `remote up` | Gives access to the user's model accounts, to MCP servers and to the Workers of the Cloudflare account the user allowed |
| User files | The project, and everything else the user can read or write (home, dotfiles, SSH and cloud credentials, other repositories) | Confidentiality and integrity of the user's work and machine |
| Shell | The ability to run commands as the user | Equivalent to the user's whole account |
| The app's own configuration | `~/.<command>/` and the project's `.<command>/` (settings, hooks, tools, MCP servers) | Writing it grants permissions or runs code on the next run |
| Model accounts | The provider accounts the app is connected to | Cost, quota, and the standing of the account with the provider |
| Session data | Transcripts, trace, memory, checkpoints in the data folder | May contain source code, secrets pasted or printed, and prompts |
| The local web page | A loopback HTTP server with a per-process token | Shows session data and can attach a terminal to a session |
| The machine's remote key and paired devices | `remote/` in the data folder, readable only by the user; each phone's key in its page's IndexedDB | The machine key answers for the machine to every phone; a device key opens the console from anywhere the relay is reachable, terminal included |

## Actors

| Actor | Trust | What they control |
|---|---|---|
| The user | Trusted | The terminal, the settings in the user folder, answers to questions |
| The model under prompt injection | Untrusted | Every tool call and its arguments. Anything the model read (a file, a web page, a tool result) may be steering it |
| A hostile repository | Untrusted until the user trusts the folder | Files in the project: `.<command>/settings.json`, `settings.local.json`, hooks, script tools, rules, instruction files, `mcp.json`, script MCP servers, declared providers, language-server configuration |
| A hostile web page or MCP server | Untrusted | The content returned by web fetch and search, MCP tool and resource results, MCP server metadata (names, descriptions, input schemas) and OAuth endpoints, redirects |
| A package registry or download host | Untrusted beyond its checksum | What a language-server install fetches |
| The relay and the network to it | Untrusted for content; trusted to serve the page | Which frames pass, when, between which channels; the page's code a phone loads. It holds no key: it can drop, delay or replay ciphertext, or claim a machine id, but not read or forge a channel. A relay that serves a hostile page can take the device key of a phone that loads it |
| Whoever holds a paired phone | Trusted as the user until the device is revoked | The console through the tunnel, the terminal included |
| Another local user or process | Untrusted | Other ports on loopback, the shared temporary directory, a browser on the same machine. A process running as the same user is out of scope: it can read the vault key from `secrets.key` when the key is kept there, and can ask the keychain for it otherwise (macOS may ask the user first; an unlocked Secret Service collection does not) |

## Trust boundaries

1. **User folder vs project folder.** Settings in the user's folder may grant (allow rules, extra directories, MCP approval, script access, feature flags, `sandbox.allowWrite`). A project's versioned settings may only restrict (deny and ask rules, turning a security feature on, `sandbox.network: false`, `sandbox.required: true`); a project's `mcp.json` cannot take a stdio server out of the sandbox or widen where it writes, only keep it off the network. Deny always wins over allow and ask rules and over every mode, bypass included, for what the rules can see; a shell line whose program they cannot see (see SEG-8) is asked about every time, in every mode, while a deny rule could name it. The boundary is drawn by workspace trust (`decisions/0004-workspace-trust.md`): until the user trusts a folder, nothing in it runs code or grants anything, `settings.local.json` included, and no language server is installed for it; the answer is kept in the data folder and reaches the engine from the handler, never from the client's request. A trusted folder is trusted whole, and stays trusted when its content changes. Trust does not cover the repository's own git configuration: every git command the app starts itself (the prompt's git snapshot, the change tracking around each shell command, worktrees, `/check`, the changes view, the first commit, plugin clones) goes through one hardened helper, `platform::git::command`, that runs none of the programs a `.git/config` can name (SEG-19), in a trusted folder or not. A settings file that does not read, in a layer that is not the owner's (the project's `settings.json`, an untrusted `settings.local.json`, a `.<command>/` folder above the project), is skipped with a notice naming the file instead of stopping every run; the owner's own files (`~/.<command>/`, a trusted folder's `settings.local.json`) still stop the run until fixed (`crates/agent-engine/src/prompt/settings_trust_tests.rs` `a_broken_settings_file_a_folder_brings_is_skipped_with_a_notice_and_the_run_goes_on`, `a_broken_settings_file_the_owner_wrote_still_stops_the_run`). Skipping costs the restrictions that file would have added.
2. **Model vs tools.** Every tool call is first checked against the JSON schema the model was given for that tool (an invalid input is returned to the model as an error naming the field; its effects are never computed and nobody is asked). It then passes one permission decision, `domain::permission::PolicyEngine`, judging the effects the tool declares in Rust for that input (paths resolved, shell commands parsed): mode, rules, forced questions for risky commands, sandbox exits, a required sandbox the system cannot provide, and package concerns. Every script's calls to the host (`ctx.readFile`, `ctx.writeFile`, `ctx.exec`, `ctx.fetch`) must be declared (a script tool in `spec.capabilities`, a hook or skill script in `export const capabilities`, a script MCP server in its default export), granted by the `scripts.*` settings, and are then judged as `Read`, `Write`, `Bash` and `WebFetch` calls by the same engine: a script tool's through the agent, the others' through the run's host judge, which asks the user where the policy asks and, where nobody can be asked, refuses and names the rule that would allow the call. Declared providers and prompts have no host functions. Installing a missing language server is an effect of the `LSP` call that would start it (`Effect::Install`), asked in every mode including bypass, refused while planning, and refused where nobody can be asked unless the owner's rule `LSP(install:<server>)` allows it. Hooks and, in bypass, a classifier that fails closed sit around the engine (`decisions/0003-effects-based-permission-policy.md`).
3. **Project boundary on the file system.** Reading tools ask before reaching outside the project and added directories; writing tools ask before writing outside them, into a `.git/` folder or into the app's own configuration folder, judged by where the path really leads.
4. **External content vs instructions.** Text written by someone other than the user is fenced: a fetched web page is fenced and read by a separate model before the main model sees it; the result of an MCP tool or resource reaches the model inside an `<untrusted-content>` fence that names the server and says it is data, not instructions; an opening or closing fence tag inside the text, in any letter case, is escaped. Every tool result has invisible characters removed and the app's own markers escaped. Inbox notices are marked as data.
5. **Scripts vs the host.** JavaScript hooks, tools, skills, providers and MCP servers run in an embedded QuickJS runtime whose only way out is a host bridge. Every run has a 64 MiB memory limit, a 1 MiB stack limit and a time limit (wall clock for hooks, prompts and skill scripts; a 60-second budget of running time, not counting waits on the app, for script tools and script MCP servers). A project's scripts get no file, process or network access unless an owner layer grants it (`scripts.*`); every script must also declare each host function it uses, and each call is judged by the policy engine (boundary 2). A command a script starts runs through the same confinement as a command hook.
6. **Process vs operating system.** An optional write sandbox (the `experimental-sandbox` feature, on by default) confines shell commands the agent runs, command hooks, background test runs, commands started by scripts and script MCP servers, and stdio MCP servers: `sandbox-exec` on macOS, Landlock on Linux (5.13 or later). Where the system cannot provide it, the run says so once; with `sandbox.required` (on by default on Linux and macOS, turned off only by the owner) every confined command is refused and stdio MCP servers do not start, otherwise they run unconfined (the default on Windows). On macOS the profile also denies writes to the `.<command>/` folder of the project, of each added folder, of a session worktree's repository and of the home folder, and to `.git/config`, `.git/config.worktree` and `.git/hooks` of each of those roots once its `.git` exists (a writable folder inside a guarded one, such as a session worktree, stays writable, and its own guards apply again); it denies starting `/bin/launchctl`, looking up Launch Services and sending AppleEvents (SEG-20). Landlock can only allow folders, so on Linux none of these carve-outs exist and the hardened git of boundary 1 is what keeps a written `.git/config` from running anything on the host.
7. **Browser vs the local web page.** Loopback only; the link carries a one-time entry code in its fragment (two minutes, used once), which the page trades for the console's token and keeps in its own per-origin storage; every `/api/` request carries the token itself (an `Authorization` header, or the query of an event stream or socket), never a cookie, since a browser sends a `127.0.0.1` cookie to every port; a `Host` and origin check.
8. **Phone vs machine, across the relay.** The machine listens on nothing new: it connects out to the relay its owner set. Every phone channel is a Noise session (`IK`, or `IKpsk2` while pairing) between the phone's static key and the machine's; the machine accepts only a recorded device, or a pairing whose one-time code is still pending (single use, ten minutes). The code travels in a link fragment, never sent to the relay. Inside the channel only `/api/` requests are forwarded, to the console on loopback with its own cookie, so the console's guard and limits still apply (`decisions/0012-remote-control-through-a-blind-relay.md`).
9. **Secrets at rest.** Entries are encrypted with XChaCha20-Poly1305 and bound to their entry name; both files are readable only by the user. By default the key sits in `secrets.key` beside the vault, readable only by the user: anyone who can read the data folder as that user, or a copy or backup of it, can open the vault. With `<PREFIX>_SECRETS=keychain` the key moves to the system keychain (macOS Keychain, Secret Service, Windows Credential Manager) and `secrets.key` only points there; then a keychain that stops answering is an error, never a new key (`decisions/0006-one-persistence-pattern.md`).

Controls that later work must not weaken: deny rules always win, in every mode, for every command the parser can see, and a command whose program it cannot see is asked about every time while a deny rule could name it (SEG-8); the sandbox never lets a confined command write a toolchain or unpacked packages (SEG-24); agent edits and rewinds replace files whole (SEG-27); untrusted layers can only restrict; the bypass classifier fails closed; secrets are kept out of debug output; language-server downloads are checked against a pinned SHA-256 and npm installs never run package scripts; tool input is checked against its schema before anything else; the console is loopback-only with token and origin check; OAuth uses PKCE S256 and `state`; no shell command is built by concatenating configuration data; the app starts git only through `platform::git::command` (`xtask lint` fails otherwise); `Read` rules judge every path a read-only shell command names.

## MCP servers a project brings

A project's stdio servers (`.<command>/mcp.json`) and script servers (`.<command>/mcp/*.js`) start only in a trusted folder and only after their own approval (`enabledMcpServers` or `enableAllProjectMcpServers` in an owner layer); approval alone starts nothing in an untrusted folder (`crates/agent-engine/src/mcp/configured.rs`, test `a_run_gets_the_project_s_approved_servers_and_the_user_s`). A stdio server is a `platform::child::Child`: its own process group, stopped and reaped with the session. When the sandbox is on it starts inside it, with the writes of a shell command plus what the owner's entry adds, and the network on unless the entry turns it off; only the owner's `mcp.json` (or `--mcp-config`) can opt a server out, and with a required sandbox the system cannot provide it does not start (`crates/agent-engine/src/mcp/stdio_sandbox.rs`). It still inherits the environment (SEG-9). A script server runs in the script runtime with the limits of boundary 5, the project's `scripts.*` grants, the capabilities it declares, each call judged by the run's host judge, and, when the sandbox is on, its `ctx.exec` confined like a command hook.

## Not yet covered

- The web terminal (a WebSocket to a pseudo-terminal running the app's own binary): it has had no security review of its own as of 2026-11-17. It is also reachable from a paired phone through the relay, on by default by the owner's decision (`decisions/0012-remote-control-through-a-blind-relay.md`).
- Files in the shared temporary directory (per-run MCP configuration, memory edits, large tool results), some of which are not private today.
- Plugins: installed by `git clone` into the user folder and loaded as user-level content.
- MCP server metadata as an injection channel: tool descriptions and schemas reach the model's tool list unfenced.
- Supply chain of the build, beyond what `cargo deny` checks: the `deny` job in CI (`.github/workflows/ci.yml`, configured by `deny.toml`) fails on RustSec advisories, unlisted licences, wildcard versions and non-crates.io sources, but nothing reviews the code of a new or updated dependency.
