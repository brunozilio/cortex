# Glossary

The project's own vocabulary. Code carries no comments (see `decisions/0010-comments-stay-out-of-code.md`), so a name is the only documentation next to the code and this file is where a name is explained. Paths are relative to the repository root and point at the main place a term lives as of 2026-11-17; a record in `decisions/` that moves one says so.

The product is written as "the app", its binary as `<command>`, its project folder as `.<command>/` and its user folder as `~/.<command>/`.

## Runs and sessions

**Run.** One execution of the engine: one prompt (or one session command such as compact or rewind) from start to a terminal event. It has a `RunId`, is a task of the engine runtime (its synchronous loop runs on one of the runtime's blocking threads) and ends with exactly one of `Completed`, `Failed`, `Cancelled`. Lives in `crates/agent-engine/src/engine/mod.rs` and `engine/task.rs`; the events are in `crates/domain/src/run/events.rs`.

**Engine.** `agent_engine::Engine`, the agent engine built into the app and the one implementation of the `AgentEngine` trait (`crates/agent-engine/src/boundary/mod.rs`), the seam the backend starts runs through and tests replace. It was called `NativeEngine` while other engines were planned. The app builds it in `crates/app/src/engine.rs` (`engine::build`), with `ProviderApis`, the `ApiSource` that turns a run's keys into model clients. Lives in `crates/agent-engine/src/engine/mod.rs`.

**Engine runtime.** The one multi-threaded Tokio runtime the engine and model HTTP share: built once per process on first use, with at most four named workers (`engine-worker`) and at most 256 blocking threads (`engine-blocking`). `Engine` takes its handle when it is built and starts each run on it; synchronous code reaches async code through `platform::runtime::block_on`, which waits on the calling thread and, called again inside such a wait, serves the inner wait on a short-lived thread instead of deadlocking. The console keeps its own runtime. Lives in `crates/platform/src/runtime.rs`. See `decisions/0007-one-async-runtime.md`.

**Stop (cancellation).** A run's cancellation: a `CancellationToken` that async code awaits plus the flag that synchronous code not yet moved to async reads. Cancelling sets both at once, so a wait on the token ends immediately and a flag reader sees it at its next check. `Control` and `Workspace` hold the run's `Stop`; a sub-agent's control gets its own, cancelled with its parent's. A hook gets a child of the run's token, so its timeout ends the hook and not the run. A bridged channel server (a domain `McpEndpoint`) is handed the run's own `Stop` by the in-process transport. Lives in `crates/platform/src/stop.rs`; a control's is reached through `Control::token`.

**Turn.** One iteration of the agent loop inside a run: one model call plus the tool calls that reply asked for. A run has at most 200 turns. It does not mean "one user prompt and its answer"; that is a run. The TUI also has a `Turn` struct (`crates/cli/src/tui/turn.rs`) that holds the state of the run in progress, which is a different thing. Lives in `crates/agent-engine/src/agent/turn/`; the limit, `MAX_TURNS`, is in `crates/agent-engine/src/agent/mod.rs`.

**Turn state / transition.** The agent loop is a state machine. `TurnState` is what one run of the loop carries from step to step (the history, usage, fallbacks, reminders, cut-offs). `Next` is the step to take: ask the model, take its reply, run the tools it asked for, finish, or done. A transition is one such step: `Agent::turns` matches on `Next`, each handler returns the next one, and after every step that is not a model call `ThisRun::transition` hands the history to whoever keeps it. See `decisions/0002-agent-loop-state-machine.md`. `TurnState`, `Next` and `Agent::turns` live in `crates/agent-engine/src/agent/turn/mod.rs`; `ThisRun` in `crates/agent-engine/src/agent/run.rs`.

**Session.** A conversation kept on disk and continued across runs. It has a `SessionId` (a free string, a UUID when the engine creates it) and belongs to one project folder. Its conversation is read from disk at every run; what is costly to rebuild stays in its live session between runs (see `decisions/0001-long-lived-session.md`). On disk it is two append-only files in the data folder's `native-sessions/`: `<hash>.jsonl`, the conversation, written and synced at every transition of the turn, and `<hash>.trace.jsonl`, the trace; `<hash>` is the SHA-256 of the fixed legacy tag `LocalOwner`, the canonical project path and the session id. Resuming reads the first only. Lives in `crates/agent-engine/src/sessions/mod.rs`.

**Live session.** What the engine keeps in memory for a session between its runs: its session cache, its MCP pool, and whether `SessionStart` has fired. It is entered when a run has loaded the session, so a chore (title) or a rewind enters none. At most eight are kept, least recently used out first; one in the middle of a run is never let go. It ends when it is pushed out or when the engine is dropped: `SessionEnd` fires then, if `SessionStart` did, and its MCP servers are terminated and waited for. Not to be confused with the TUI's fleet, which is what the terminal shows. `LiveSessions` and `LiveSession` live in `crates/agent-engine/src/engine/live/mod.rs`.

**Session cache.** The part of a live session that keeps the Brief (with its settings and hooks) and the script tools from one run to the next. Before each run a fingerprint of the files they are read from is taken: path, modification time, size and, for files up to 64 KiB, a hash of the content. The settings files and instruction files of the project, its parents and the owner's folder; the skills, commands, agents, rules, hooks, plugins, styles and tools folders; nested instruction files; the host's plugin and extra folders. The same fingerprint reuses what was loaded; any difference loads it again at that run's start, never in the middle of a run. What is not a file (environment, git state) is not watched. Lives in `crates/agent-engine/src/engine/live/cache.rs` and `sources.rs`.

**MCP pool.** The MCP servers a live session keeps connected across its runs. Each run asks the pool for the servers its settings, trust and approvals allow now; a server whose entry is unchanged and whose process is alive is reused, a new or changed entry is started, and one that is no longer wanted (removed, changed, approval revoked) is terminated and waited for. In-process servers (the host's own and script servers) are opened per run. Lives in `crates/agent-engine/src/mcp/pool.rs`.

**RunStart / RunEnd.** Hook events that fire once per run: `RunStart` after `SessionStart` (which fires only on a live session's first run) and before `UserPromptSubmit`, with the same input as `SessionStart` and its context added to the prompt; `RunEnd` when the run closes, whatever its outcome, before the conversation is saved. They took over what `SessionStart` and `SessionEnd` did before the live session. Fired from `crates/agent-engine/src/engine/live/events.rs` and `crates/agent-engine/src/engine/phases/close.rs`.

**Transition.** A step of the turn's state machine after which the conversation is on disk: before a model call, after its reply is recorded, after a batch of tool results. A process that dies loses at most what happened since the last one; a tool call left without its result is closed as interrupted on resume. See `decisions/0002-agent-loop-state-machine.md`. Lives in `crates/agent-engine/src/agent/turn/mod.rs`.

**Amendment.** A conversation log entry, written as `truncated` with `amended: true`, that cuts the kept conversation back to the first message that changed before the new version of it is appended; a reminder added to tool results that were already saved is the usual cause. It is not a rewind and the trace does not show it as one. Lives in `crates/agent-engine/src/sessions/log.rs`.

**Job.** The object that prepares and drives one run. It is not a queue entry and there is no scheduler; "job" and "run" have the same lifetime. Lives in `crates/agent-engine/src/engine/job.rs`.

**Phase (engine).** One of the eight typed steps `Job::phases` runs in order for a run: `load_session`, `brief`, `equip`, `apply_policy`, `prepare_runtime`, `open`, `drive`, `close`. Each takes what the one before produced; a phase that ends the run early returns a `Stop`, which is turned into the run's last events in one place. A phase is not a turn (a step of the agent loop, inside `drive`). The list is in `crates/agent-engine/src/engine/job.rs`, each phase in `crates/agent-engine/src/engine/phases/`, `Stop` in `crates/agent-engine/src/engine/stop.rs`.

**Run gate.** The point every engine event passes through on its way out. It lets exactly one terminal event through and nothing after it, so a caller can rely on a run ending once. Lives in `crates/agent-engine/src/boundary/gate.rs`.

**Brief.** What the engine gathers from a folder before a run: plugins, settings, skills, agents, rules, instruction files and a git snapshot. It is kept in the session cache and loaded again only when a file it was read from changed, so a `Brief` hook runs at a live session's first run and after such a change, not at every run. `Brief` is also the name of a hook event that may rewrite that result, and `MemoryBrief` (`crates/domain/src/knowledge/memory/brief.rs`) is the unrelated piece of memory that goes into a request. Lives in `crates/agent-engine/src/brief.rs`.

**Checkpoint / rewind.** A checkpoint is taken once per prompt and keeps the previous content of every file the run edited, with the position in the conversation. Rewind restores those files and cuts the conversation back to that prompt (the cut is skipped if a compaction changed the history since). Branch starts a new conversation from before a prompt. A session keeps the files of its newest 50 checkpoints and at most 64 MiB of them, in `native-sessions/checkpoints-<hash>.json`; an older checkpoint keeps its place in the list but not its files, so it can be branched from and not rewound to. Lives in `crates/agent-engine/src/checkpoints.rs`. The `Checkpoint` in `crates/cli/src/tui/rewind.rs` is the TUI's row for one of them in the rewind list.

**Upkeep / compaction.** Upkeep is the module that keeps a conversation inside the model's context window: it measures usage, replaces old tool results with a marker, and compacts. Compaction asks the model to summarise the older part of the history and keeps the most recent tail verbatim. It runs automatically near the limit, after a "too long" error from the provider, or on `/compact`. Lives in `crates/agent-engine/src/upkeep/`.

**Chore.** An auxiliary model call made around a run, not part of the conversation: session title, next-prompt suggestion, recap on resume, side question, heads-up, branch name, lesson. The TUI starts several after each completed run, so they cost model calls the user does not see. A chore is not a background job and is not recorded in the session catalog. Lives in `crates/agent-engine/src/chores/mod.rs`; triggered from `crates/cli/src/tui/chores.rs`.

**Steer.** Text the user sends while a run is in progress. It is queued and delivered to the model with the next tool results or at the end of the turn; "unsteer" takes back what was not delivered yet. It does not interrupt the run. Lives in `crates/agent-engine/src/control.rs`.

**Ask.** A question the engine puts to the user in the middle of a run, which waits for the answer: a permission request, a set of questions, or a plan approval. The type is `AgentAsk`; the answer is a `Decision`. "Ask" is also the name of a permission mode and of a rule kind. Lives in `crates/domain/src/run/approval.rs`.

**Fleet.** The sessions that are live in one terminal process, shown by `/fleet`. It is a list of sessions, not a group of agents or machines. Lives in `crates/cli/src/tui/fleet/mod.rs`.

**Mirror.** The copy of the screen of the session a terminal process shows, sent to the console's terminal view while a page watches it. The page sees exactly what the terminal shows, at the terminal's size, and its keys go to that same session; it is not a second process resuming the session. Lives in `crates/console/src/mirror.rs`; the copying in `crates/cli/src/tui/mirror.rs`, the key decoding in `crates/cli/src/tui/mirror_keys.rs`.

**Outside runs.** Runs of the session on screen that another process made: the console's page, a phone through remote control, or another terminal resuming the same session. While the terminal is idle, the `outside_runs` TUI feature checks the session's length once a second and, when it grew, reads its new records and adds them to the transcript, so the screen shows what was done elsewhere. It was the `elsewhere` folder until 2026-11-17. Lives in `crates/cli/src/tui/features/outside_runs/` (`watch.rs` decides when to look).

**Parked session.** A live session in the fleet that is not the one on screen. Its state is held aside and swapped into the TUI's `App` when one of its events arrives. Lives in `crates/cli/src/tui/fleet/parked.rs`.

**Carried / run watch.** What a client's session carries from one run to the next: the session id, the permission mode, what was spent against the budget, the verification criteria, the corrections a lesson may be drawn from and a pending fork. `Carried::observe` applies a run's events to it, and `Touches` says what a run of a given `SessionCommand` may change: a prompt changes everything, a session command (compact, rewind, branch, measure) only the session id, a chore nothing but the spending. `RunWatch` is the per-run part, which also follows the plan being written (`PlanWatch`: the plan presented for approval, else what a planning run said). The rules live in `crates/domain/src/run/session_run.rs` and `crates/domain/src/run/verification/plan_watch.rs`; the client holds the lock in `crates/app/src/client/session.rs` and `crates/app/src/client/run.rs`.

**Peer.** Another client in the same process, registered under a name built from its folder and client number. The `ListSessions` tool lists peers and `SendMessage` can address one. Lives in `crates/agent-engine/src/tools/peers.rs`.

## Permissions

**Permission mode.** How much the agent may do without asking: `Ask`, `AcceptEdits` (the default), `Plan` (no edits, no execution), `Bypass`. Each has one name the app shows, writes and documents, `mode_label`: `ask`, `edits`, `plan`, `bypass`. On input (`--mode`, `/mode`, the saved `mode`, a sub-agent's `permissionMode`) `mode_named` also reads the aliases in `MODE_ALIASES`, in any letter case: `default` for ask, `acceptEdits` and `accept-edits` for edits, `bypassPermissions`, `bypass-permissions` and `yolo` for bypass; a sub-agent may also say `dontAsk`. Run events and request JSON keep the variant names (`"AcceptEdits"`), and a script tool's `ctx.mode` keeps the lowercased variant (`acceptedits`) it always had. There is no fifth "auto" mode: the safety classifier that reviews actions in bypass and the automatic model picker are separate mechanisms. The type lives in `crates/domain/src/run/approval.rs`, its names in `crates/domain/src/command/mod.rs`.

**Effect.** What one tool call will do, declared by the tool in Rust from its input (`Tool::effects`): read a path or a folder tree, write a path, execute a parsed shell command, reach a network host, spawn work (a sub-agent, a background shell, a schedule, a watch), cancel work (its own or not), notify the user, message another session, read an MCP resource, call an MCP server, or the coarse class a user script tool declares (`Declared::Edits`, `Declared::Executes`). A call with no effects only reads state the agent owns. Paths carry both the path as written and where it really leads (symlinks resolved). Lives in `crates/domain/src/safety/permission/effect.rs`. There is no per-tool `access` class any more; `Access` in `crates/domain/src/models/model.rs` is unrelated: it is how a provider is signed in to (key, browser, code).

**Policy engine / verdict.** `PolicyEngine::decide` judges a call (tool name, subject, effects) in a `PolicyContext` (mode capped by a sub-agent's ceiling, project roots and added folders, protected locations `.git/` and the app's own configuration folder, allow/ask/deny rules, remembered answers, sandbox, whether the user can be asked) and returns a `Verdict`: `Allow`, `Ask { reason, rememberable, rule }` or `Deny(reason)`. The reason says why it asks (the mode, a rule, a hook, reading outside, a guarded write, a risky command, an address, leaving the sandbox, a package concern, installing a language server). `rememberable` says whether the question offers "don't ask again": only where that answer stops the next question (the mode, reading outside, a guarded write, installing a language server); a rule, a hook, a risky command, an address, leaving the sandbox or a package concern ask again every time, so the question offers no "don't ask again" (`Reason::rememberable`). An `Effect::Install` (a language server the `LSP` call would install first) is asked in every mode, bypass included, and refused while planning, unless a rule naming it (`LSP(install:<server>)`, never a bare `LSP`) allows or denies it; where nobody can be asked the refusal names that rule. Hooks, the bypass safety classifier and the question to the user are orchestration around it in `crates/agent-engine/src/agent/permission/`. Lives in `crates/domain/src/safety/permission/`; see `decisions/0003-effects-based-permission-policy.md`.

**Shell command / opaque.** A Bash command line parsed by `domain::shell` into every simple command it runs, including those inside control structures, function bodies, subshells, command and process substitutions and `find -exec`. A line the parser cannot follow with confidence is opaque: never read-only, never allowed by a rule with a specifier, and asked about when a deny or ask rule with a specifier exists. Lives in `crates/domain/src/safety/shell/`.

**Trust (workspace trust).** The user's stored answer to "may this project folder run code and grant itself permissions?". It is `Trust::Trusted` or `Trust::Untrusted`, kept per trust root (the nearest ancestor containing `.git`, else the folder itself; never the home folder or a file-system root) in `users/local/trusted-folders.json`, and handed to the engine by the handler as `Extensions.trust`. In an untrusted folder the engine's `Gate` skips project hooks, scripts, MCP servers, declared providers, language-server commands and the owner reading of `settings.local.json`; instruction files and deny or ask rules still apply. It is not a per-item approval (a trusted project's MCP server still waits for its own), not the `trusted` field of a found skill or script tool (which says whether a script is the owner's or the project's, for script access), and not "untrusted content" (text the model read). A `Contributions` is the typed list of what a folder brings that trust would enable; a `TrustReport` is the state plus that list. See `decisions/0004-workspace-trust.md`. The rule is in `crates/domain/src/safety/trust/`, the gate and the scan in `crates/agent-engine/src/trust/`, the store in `crates/app/src/trust.rs`.

**Sandbox / confinement.** The `experimental-sandbox` feature: shell commands the agent runs (Bash, Monitor, a script's `ctx.exec`, a script MCP server's `ctx.exec`, command hooks) and stdio MCP servers start confined so they write only in the project, added folders, the temporary folders, package caches and `sandbox.allowWrite`. On macOS it also keeps commands from reading credential stores in the home folder and the app's data folder (`Confinement.unreadable`; the owner's `sandbox.allowRead` reopens a path, `Confinement.readable`), and from moving or removing a folder that holds a guarded path (pinned in the profile). A `Confinement` is that list for one run (`crates/domain/src/safety/sandbox.rs`, `crates/platform/src/sandbox.rs`); it is applied by `sandbox-exec` on macOS and by Landlock on Linux (`crates/platform/src/linux/landlock.rs`). `platform::sandbox::support()` says whether this system can apply it and, when it cannot, why. Where it cannot, the run says so once (a harness notice); with `sandbox.required` (true by default on Linux and macOS, `REQUIRED_BY_DEFAULT`; only the owner turns it off) the policy engine refuses every confined command (`sandbox_missing` in `PolicyContext`) and stdio MCP servers do not start, otherwise both run unconfined. A stdio MCP server's own entry in `mcp.json` may add folders (`sandbox.writable`), keep it off the network (`sandbox.network: false`, network is on by default for servers) or, from the owner's file only, opt out (`"sandbox": false`); that entry is a `ServerSandbox`, settled per run into a `StdioSandbox` (`Confined`, `Unconfined` or `Refused`) in `crates/agent-engine/src/mcp/stdio_sandbox.rs`. It is not workspace trust and not the script runtime's own limits.

**Fence (untrusted content).** The `<untrusted-content>` wrapper put around text the model reads that someone other than the user wrote: a fetched page (before the reader model sees it) and the result of an MCP tool or resource (before the main model sees it). It ends with a line saying where the text came from and that it is data, not instructions; any opening or closing tag inside the text, in any letter case, is escaped so it cannot close the fence. Lives in `crates/domain/src/safety/untrusted.rs`.

**Permission rule.** An allow, ask or deny line, written `Tool` or `Tool(specifier)`. Deny wins over ask, ask over allow; with no rule the mode decides. Lives in `crates/domain/src/safety/permission_rules/mod.rs`.

**Permission decision.** Allow, ask or deny: what a rule says (`RuleKind`) and what a `PreToolUse` or `PermissionRequest` hook answers (`permissionDecision`, `decision.behavior`). One enum serves both; `PermissionDecision` is its name where a hook gives it. A hook that answers any other word fails. Lives in `crates/domain/src/safety/permission_rules/mod.rs`.

## Models

**Provider vs vendor.** A provider is a way to reach models: an endpoint plus an authentication method (an API key, a sign-in). A vendor is a model family: its prices, aliases and reasoning rules. The same vendor's models can be reached through more than one provider. The `Provider` trait is in `crates/llm-providers/src/lib.rs`, one folder per provider is in `crates/llm-providers/src/providers/`, and `Vendor` is in `crates/llm-providers/src/vendor.rs`.

**Wire.** The request and streaming format of a model API: `chat`, `messages`, `responses`. A provider names the wire each of its models speaks. It is not the protocol between the terminal and the backend. Lives in `crates/llm-providers/src/model/wires/`.

**Idle deadline (stream).** How long a model stream may send nothing, before its headers or between two chunks, before the turn fails with `ModelError::Stalled`: 300 seconds, or the number of seconds in `<PREFIX>_STREAM_IDLE_SECONDS`. A stream that keeps sending has no total deadline. A stall counts as a network failure: it is retried when nothing was shown yet and can move the run to a fallback model. Lives in `crates/llm-providers/src/model/http.rs` (`stream_idle`) and `model/body.rs`.

**Retry-After / backoff.** A busy or unreachable provider is asked again up to four times while nothing of its answer has been shown. Between attempts the wait doubles from the wire's backoff (2 s) and is jittered to between half and all of it; a refusal that says how long to wait (`retry-after-ms`, `retry-after` in seconds or as a date) is waited for exactly that long instead, and one that asks for more than 60 seconds is given up at once. Lives in `crates/llm-providers/src/model/retry.rs`.

**Model roles: small model, advisor, judge.** A session can assign different models to different jobs. The small model does cheap auxiliary work, such as reading a fetched web page before the main model sees it. The advisor is a second model the agent can consult through the `Advisor` tool. The judge is the model that decides whether a run met its verification criteria. Other roles are plan, explore and review. Roles are in `crates/domain/src/models/model_roles/mod.rs` and resolved in `crates/agent-engine/src/engine/roles.rs`.

**Verification.** Criteria that a run's result is judged against when it finishes, taken from the user, from the plan, or from the project's `verification.md`. A failed verdict sends the agent back to work, up to three attempts; nothing is verified in plan mode. It is not the `verify` skill and not the repository's own test gate. Lives in `crates/domain/src/run/verification/mod.rs`.

## Configuration

**Workspace vs project.** `Workspace` is an engine type: the per-run context handed to every tool (folders, policy, models, services). It is not a folder and not the Cargo workspace. The project is the folder the user works in, with the `.<command>/` folders of it and its ancestors. "Workspace trust" in `decisions/0004-workspace-trust.md` is about the project folder (see **Trust**). `Workspace` lives in `crates/agent-engine/src/tools/workspace/mod.rs`.

**Settings vs UI state.** Settings are the configuration files a user or a project writes: `~/.<command>/settings.json`, `<project>/.<command>/settings.json` and `settings.local.json` (rules, hooks, flags, model roles). They are read by `crates/agent-engine/src/prompt/settings.rs`. UI state is what the TUI remembers for itself (model, mode, prompt history, last session per folder), stored in the data folder. The code calls both "settings"; the UI state is written by `crates/cli/src/tui/settings.rs` through `crates/app/src/settings.rs`, as a list of `SettingsChange` applied under the file's lock rather than as a whole document.

**Document (persistence helper).** A JSON (or text) file that is read, changed and replaced whole under one policy: cross-process lock with a bounded wait, atomic replace, nothing written when nothing changed, and a file that does not parse set aside as `<name>.corrupt-<epoch seconds>` (program-owned) or reported and left alone (hand-edited). Every JSON store of the application goes through it (settings, UI state, provider accounts, the vault's entries, `mcp.json`); the session catalog and project memory are rows in the SQLite database `app.db` instead (`crates/app/src/db/`), and a session's log is append-only. See `decisions/0006-one-persistence-pattern.md`. It is not a file the agent edits for the user. Lives in `crates/platform/src/store/mod.rs`.

**Data root.** Where one instance of the application keeps everything it owns: the folders for UI state, provider accounts, the code-map cache, session logs, language servers, the vault and `app.db`. `DataRoot::system()` is the user's real data folder, `DataRoot::under(folder)` puts all of it under one folder (`Client::builder().data_dir`, used by tests), and `DataRoot::in_memory()` keeps nothing on the machine. It also opens the stores; when `app.db` cannot be opened it falls back to stores that last as long as the process and records why, which reaches the user once as a harness notice. It is not the project folder and not `~/.<command>/`. Lives in `crates/app/src/data_root.rs`; the recorded reason is a `Degraded` (`crates/app/src/degraded.rs`).

**Feature vs feature flag.** A feature is a folder of code that plugs into a host: `crates/app/src/features/<name>/` on the backend and `crates/cli/src/tui/features/<name>/` in the TUI. A feature flag is a named on/off switch in the settings' `features` key, defined in `crates/domain/src/features.rs`; every flag is on unless turned off, except the opt-in ones (`experimental-code-mode`), which are off until the owner turns them on. A backend feature is turned off only through its switch, the flag `FeatureName::switch` names for it (`crates/app/src/api/features/mod.rs`; the flags that exist only for that are in `crates/domain/src/features/backend.rs`); `flags`, `sessions`, `shell` and `workspace` have none and are always on. A name that is not a known flag switches nothing. A Cargo feature is a third, unrelated thing.

**Content.** The `content/` folder: prompts, tool descriptions, hooks, output styles, built-in agents and skills, written in JavaScript and Markdown and embedded in the binary at build time. A file with the same path under `~/.<command>/` overrides the embedded one. It does not mean message content. The `content` crate is in `crates/content/src/lib.rs`; the JavaScript contract is `content/types.d.ts`.

**Hook events.** The points where user code can observe or change a run. There are nineteen: `Brief`; `SessionStart`, `SessionEnd` (once per live session), `RunStart`, `RunEnd` (once per run), `UserPromptSubmit`; `ModelRequest`, `ModelResponse`, `ModelError`; `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`; `PreCompact`, `PostCompact`; `Stop`, `SubagentStart`, `SubagentStop`; `Notification`. A hook is a shell command, an HTTP call, a script, a model prompt or a sub-agent. The events are the enum `HookEvent` and the five kinds of handler the enum `HandlerKind` (`command`, `script`, `http`, `prompt`, `agent`), both in `crates/domain/src/tools/hooks.rs` and written in settings as the same words; `HookEvent::may_ask_a_model` says on which events a prompt or agent hook may run. A settings key that is no event, or a `type` that is no kind, is refused by name before the hooks are read (`crates/agent-engine/src/hooks/validate.rs`).

**Script tool.** A tool a user or project writes in JavaScript under `.<command>/tools/`, run in the embedded QuickJS runtime. It is distinct from the `content/tools/<Name>.js` files, which describe and wrap the built-in Rust tools. Lives in `crates/agent-engine/src/tools/script_tool.rs`; the runtime is `crates/script/src/lib.rs`.

**Host bridge (script).** How a script's host calls (`ctx.*`) reach the agent: the script runs on its own thread and each call is sent to the calling thread, which serves it and sends the answer back; the script's end is sent the same way, so the wait ends the moment the script does. One bridge, `script_bridge::hosted`, serves script tools and hook scripts. Lives in `crates/agent-engine/src/tools/script_bridge.rs`.

**Capability (script) / host call / host judge.** A host function a script must declare before it may call it: `readFile`, `writeFile`, `exec`, `fetch` (`Capability`, `Capabilities` in `crates/agent-engine/src/tools/script_tool.rs`). Where it is declared depends on the kind (`Declaration`): a script tool in `spec.capabilities`, a hook or skill script in `export const capabilities`, a script MCP server in its default export's `capabilities`; a declared provider and a prompt have none (`Declaration::Nowhere`). An undeclared call fails naming the missing entry and where it goes; a declared one must also be granted by the `scripts.*` settings (`ScriptAccess`), and is then judged as the tool that does the same thing (`Read`, `Write`, `Bash`, `WebFetch`) by the policy engine, so it can ask, be ruled or be refused. A script tool's judged call is a `HostCall` (`crates/agent-engine/src/agent/scripts/host_calls.rs`), asked through the agent like any tool call. Hooks, skill scripts and script MCP servers are judged by the run's `HostJudge` (`crates/agent-engine/src/tools/host_judge.rs`), which the engine puts in `Services.judge`: it reads the live mode and remembered answers from the run's `Control`, the rules, bounds and sandbox state from `Grounds`, and asks the user through the run's event gate; without a run (or with prompts off) a call that would ask is refused and the refusal names the rule that would allow it. It is unrelated to the `access` field, which is the coarse class of the tool call itself, and to an MCP server's "capabilities" in its handshake.

**Script limits.** Every script run has a memory limit (64 MiB), a stack limit (1 MiB) and a time limit: a hook, a prompt or a skill script has a wall-clock limit (`script::Limit::Wall`), and a script tool or a script MCP server a budget of running time that does not count time spent waiting on the app, such as a question to the user (`script::Limit::Busy`, `script::MOST_BUSY`). Lives in `crates/script/src/lib.rs`.

**Input check.** Before a tool call is judged or run, its input is validated against the JSON schema the model was given for that tool (a built-in tool's `content/tools/<Name>.js`, an MCP server's `inputSchema`, a script tool's `spec.input`); an invalid input is returned to the model as an error naming the field, and the tool's effects are never computed. An optional field sent as `null` counts as left out. Schemas are compiled once and kept. Lives in `crates/agent-engine/src/tools/checked.rs`.

**Code mode / REPL.** The `REPL` tool, behind the `experimental-code-mode` flag: the model writes JavaScript in which every other tool it was offered is an async function, and only what the script returns or passes to `self.log` reaches the model. Each call inside a script is an ordinary tool call, with its hooks, rules and permission asks. The flag is opt-in, and with it REPL is the only tool besides the turn-level ones; every other tool is declared inside its description. The JavaScript context persists per session and agent, so what one script declares the next can read; it is a `script::session::Session`, distinct from the conversation **Session** above and from the one-shot runs of script tools. See `decisions/0011-code-mode.md`. The tool is in `crates/agent-engine/src/tools/repl.rs` and `crates/agent-engine/src/agent/repl.rs`, the context in `crates/script/src/session.rs`, the output rules in `crates/domain/src/tools/code_mode.rs`.

**Skill.** A folder with a `SKILL.md` (front matter plus instructions, optionally supporting files) that the model loads through the `Skill` tool or the user runs as `/name`. Built-in skills are in `content/skills/`. Lives in `crates/agent-engine/src/tools/skill.rs`.

**Plugin.** A git checkout under `~/.<command>/plugins/<name>/` that contributes hooks, MCP servers and language-server definitions. Lives in `crates/agent-engine/src/plugins.rs`.

**Worktree.** A git worktree the engine creates under `<repository>/.<command>/worktrees/` so a sub-agent or a session can work in isolation. It is checked out detached at the commit `HEAD` names when it is made (its base commit); uncommitted changes of the checkout are not carried over, and `EnterWorktree` says which commit and how many changes stayed behind (`Entered`). It is removed at the end if nothing changed and kept otherwise. Lives in `crates/agent-engine/src/agent_runtime/mod.rs` and `session_worktree.rs`.

**Output limit (Bash).** `domain::output::OutputLimit`: how many characters of a Bash command's output reach the model, 30,000 unless the `bashOutputLimit` setting says otherwise (kept between 1,000 and 1,000,000). Past it the command's whole output is saved under the session's tool-results folder and the model gets the start and the end under a cut note, a first line that starts with `[Output cut: ` and says how much was cut and where the whole is; the TUI shows that line unfolded. Bash is then left out of the generic persistence of large tool outputs. Lives in `crates/domain/src/tools/output/limit.rs`; applied in `crates/agent-engine/src/tools/builtin/shell/bash.rs`.

**Ripgrep candidates.** When `rg` is on `PATH`, the Grep tool asks it only for the files that could match (`--files-with-matches` with the same ignore rules, hidden files, `--text`), then reads and formats those files with the built-in engine, so both paths give the same answers; a missing or failing `rg` leaves the whole search to the built-in walk. Lives in `crates/agent-engine/src/tools/builtin/files/ripgrep.rs` and `grep.rs`.

**Child.** A process the application started and answers for, held as a `platform::child::Child`: a Bash shell, a monitor, an MCP stdio server, a language server, a hook command, a git helper. It runs in its own process group, is stopped politely before it is killed, is always waited for, and can keep the end of what it wrote to its error stream. It is not a sub-agent (a child run of the agent loop, which is a thread, not a process) and not the web terminal's pseudo-terminal process. "Grace" is how long a child is given between the polite stop and the kill; "reaped" means it has been waited for, after which nothing is signalled. See "Child processes" in `architecture.md`. Lives in `crates/platform/src/child.rs`.

## Memory and messages to the agent

**Memory kinds.** A project memory entry is `Episodic`, `Semantic` or `Procedural`. Only episodic entries decay with time; an entry given without a kind is stored as semantic. Lives in `crates/domain/src/knowledge/memory/mod.rs`. Three different stores are all called memory: project memory (per project, in the data folder), team memory (Markdown files in `<project>/.<command>/memory/`) and agent memory (a `MEMORY.md` per custom agent that declares a `memory` scope). Agent memory has no setting or environment variable that turns it off; an agent without a `memory` scope has none.

**Inbox / inbox notice / channel.** The inbox is a queue of short messages waiting to be shown to the agent during a run. An inbox notice (`domain::inbox::Notice`, a source and a text) is one such message, for example a line from a monitored background command. A channel is an MCP server that stays open for the session and pushes notices into the inbox; a channel notice carries the server's `meta` pairs and reaches the model as a `<channel source=…>` tag, other notices as `<event source=…>`. Inbox notices are treated as untrusted data and are delivered to the model, as events of the run or as a turn of their own when the session is idle. The rules are in `crates/domain/src/tools/inbox.rs`, the queue in `crates/agent-engine/src/tools/inbox.rs`, channels in `crates/agent-engine/src/mcp/channel.rs`.

**Observer / activity digest.** An observer is an agent definition named in another agent's `observer` frontmatter (up to four; `observerMessage`, `observeSubagents`). When the watched agent's turn ends, each observer is handed an activity digest: that turn's items (`domain::observer::Item`) inside a tag carrying a fresh nonce, cut to fixed sizes, followed by text saying it is data. The observer keeps its own conversation per session, watched agent and observer, and has one tool, `ObserverReport`, whose notes return to the watched agent as advice (for the main agent, it goes on once in the same turn; a sub-agent's reports go to the inbox). Observing settings travel in `Workspace::observing`, inherited two levels down. The digest rules are in `crates/domain/src/run/observer.rs`, the runtime in `crates/agent-engine/src/agent/observers.rs`.

**Team / lead / teammate / mailbox.** A team belongs to one lead session (`team-<session>` under `~/.<command>/teams/`); its `config.json` lists the members. The lead is the session's main agent, named `team-lead`. A teammate is an agent started by the lead's `Agent` call with a `name`: a separate process (`<command> teammate`, told its team and name in `<PREFIX>_TEAM_NAME` and `<PREFIX>_AGENT_NAME`) that answers its mail as a print-mode session and goes idle between messages. A mailbox is one agent's `inboxes/<name>.json`, written under a file lock; mail is text or a structured `domain::team::Protocol` message (shutdown request and answers, idle notification, plan approval). The lead's mail is moved into the engine's inbox by a watcher thread. Not to be confused with **team memory**, the project's shared memory. Rules in `crates/domain/src/run/team.rs`, store and launch in `crates/agent-engine/src/team/`, the teammate loop in `crates/cli/src/teammate.rs`.

**Permission relay.** A channel that declares `claude/channel/permission` is sent each permission prompt of its session (a five-letter request id, the tool, what it will do, a preview of its input) and may answer `allow` or `deny`; the first answer, from the terminal or any channel, settles the prompt through the control's `Answerer`. A channel cannot allow its own tools. The protocol is in `crates/domain/src/tools/channel_relay.rs`, the registry in `crates/agent-engine/src/mcp/channel_relay.rs`. The in-process message channels between threads are unrelated.

**Notice (harness) vs inbox notice.** A harness notice is something the application itself has to tell the user: keys cannot be kept on this machine, the session list and memory could not be opened. It is shown in the transcript as a notice (or printed to the error stream with `--print`), said once per process, and never sent to the model. Both kinds answer the same command, `ClientCommand::TakeNotices { for_agent }`, in the two typed fields of `Notices`: `for_user` (harness) and `for_agent` (inbox, taken only when asked for). The type is in `crates/app/src/api/event.rs`, the handler in `crates/app/src/handler/mod.rs`, the TUI side in `crates/cli/src/tui/notices.rs`. The transcript's own "notice" entry (`Transcript::notice`) is just a line the TUI shows; a harness notice becomes one.

## Requests, names and failures

**Prompt request.** What a client asks the engine to run, `domain::PromptRequest`, in four parts grouped by who sets them: `Prompt` (the user's text, images and how the prompt was shown), `SessionConfig` (folder, added folders, model, effort, which session to resume or fork, session command, output style, fallbacks, model roles, appended system text), `Policy` (permission mode, safety check, turn limit, allowed, asked and refused tools, verification criteria, budget) and `HostContext` (what the backend adds: the memory brief, host extensions, code map and the run's credentials, which never leave the process). On the wire it is still one flat object with the field names it always had. A function that needs only a folder takes a `Folder` (the folder and the host extensions), and the session store takes the folder alone, so nothing builds a request with a dummy model to call it. Lives in `crates/domain/src/run/request.rs`.

**Tool name.** `domain::ToolName`: one variant per built-in tool, `Mcp` for an MCP server's tool (`mcp__<server>__<tool>`) and `Other` for the rest (script tools, names the model made up). It is written as the plain name, so it reads every name ever stored. Code that decides by tool (which tools the loop runs itself, which run side by side, which a sub-agent may not use, which read the web) matches on it instead of comparing strings. Lives in `crates/domain/src/tools/tool_name.rs`; the engine's constants in `crates/agent-engine/src/tools/names.rs` are derived from it.

**Background started / ended.** The run events `BackgroundStarted { id }` and `BackgroundEnded { id }`, emitted beside a tool's result when it started a background command (`Bash` with `run_in_background`) or saw one end (`BashOutput` reading a finished command, `KillShell`). The transcript counts background commands from them; no tool output text is parsed. A tool reports the change in `Outcome::background`. Lives in `crates/domain/src/run/events.rs`.

**Trace mark / note title.** A `Mark` is what a trace tool node notes about itself: repeated, refused (with the reason) or an edit (with the path); a `Title` names a note node (verified, reviewed, notice, mode...). Both are written as the same strings the page reads in a span's `flags` and `name`. Lives in `crates/domain/src/trace/marks.rs`.

**Failure taxonomy.** How a failure travels from a provider to the client, each step an explicit conversion: `ProviderError` (a provider's own) becomes a `ModelError` (`crates/llm-providers/src/model/mod.rs`: unauthorized, overloaded, too long, provider, network, stalled, cancelled), which becomes a `RunFailure` (`crates/domain/src/run/failure.rs`: a `FailureKind` — usage limit, unavailable, other — and a message; `From<ModelError>`, overloaded is unavailable). The engine's `Stop` (`crates/agent-engine/src/engine/stop.rs`) is built from either (`From<RunFailure>`, `From<ModelError>`) and ends the run with the failure's two events, `Failure(kind)` then `Failed(message)`. The client turns those events back into a `RunFailure` and that into its `Error::Run` (`crates/app/src/client/mod.rs`). MCP transports fail with `McpError` (cancelled, sign-in needed, the server's own error answer, anything else; `crates/agent-engine/src/mcp/error.rs`), a language server that does not start with `StartError` and a typed shell line with `TypedError`.

## Client and handler

**Client.** `app::Client`, what the terminal holds to talk to the in-process backend: sessions, runs, memory, settings, providers, MCP servers. It is internal to the app, not an SDK for other products (`decisions/0005-typed-application-api.md`); it was called `Sdk` until 2026-11-17. `Client::builder()` makes one (`data_dir` keeps everything under one folder, for tests); `sibling` makes a second one over the same services. Each has a `Dispatcher` and its `client-dispatch` thread, which sends commands, matches replies to requests and routes run events. Lives in `crates/app/src/client/mod.rs`, the dispatcher in `crates/app/src/client/dispatch.rs`.

**Request id / reply / unsolicited event.** Every `ClientCommand` the client sends is wrapped in an `Envelope` with a `RequestId`, a number the client counts up. A `Reply` is a `ServerEvent::Reply` carrying the id of the request it answers; a request gets one terminal reply, after any number of non-terminal ones (a sign-in's "authorize at" step). A command whose handler panics is answered `internal error while handling <command>`. An unsolicited event (`ServerEvent::Unsolicited`) answers no request: the handler tells the client something that happened by itself, such as memory applied after a run or a model catalog that failed to load; the client keeps the latest 256 until they are read. Run events (`ServerEvent::Run`) are the third kind and are routed by `RunId`. The types are in `crates/app/src/api/` (`envelope.rs`, `command.rs`, `event.rs`), the waiting and routing in `crates/app/src/client/dispatch.rs`, the sending side in `crates/app/src/handler/outbox.rs`.

## Observability

**Trace / lane / span.** The trace is the record of what happened in a session's runs: prompts, events, model calls. It is written to the session's own trace file, `native-sessions/<hash>.trace.jsonl`, as the run proceeds (buffered, flushed at each transition; set aside as `<hash>.trace.1.jsonl` past 64 MiB), read back merged with the conversation log by sequence number, and projected three ways. A session written before the split has its trace inside `<hash>.jsonl`, which is still read. The first projection is a `Trace` holding a `Lane` of steps, each step a set of timed nodes. The second is a list of runs, each a tree of `Span`s (run, model call, tool, agent, task, eval, wait, event); this is what the trace page draws. The third is the report with totals and insights. Lives in `crates/domain/src/trace/`.

**OTLP export.** The opt-in copy of finished runs to an OpenTelemetry collector, on when `<PREFIX>_OTLP_ENDPOINT` is set. `domain::trace::otlp` maps a run's spans to one OTLP trace (ids derived from session and run index, model calls as `chat <model>` spans, tools as `execute_tool <name>`, figures as `gen_ai.*` and `<command>.*` attributes, never prompt or output text). The `Exporter` in `crates/app/src/features/trace/export.rs` is fed by the handler's run sink at each terminal event through a bounded queue, batches on its own thread and posts JSON with the plain HTTP client; a failure is logged once.

**Diagnostics on demand.** The LSP tool's `diagnostics` and `workspaceDiagnostics` operations: the file is synced to its server, then the server's published diagnostics are listed, the file's alone or every file the server has reported, errors first, one line each (`domain::lsp::diagnostics::listed`). Distinct from the diagnostics Edit and Write append after a change. Lives in `crates/agent-engine/src/tools/lsp.rs`.

## Remote control

**Relay.** The owner's own server that phones and the machine both connect to: it serves the page and forwards encrypted frames between a phone's WebSocket and the machine's, on numbered channels, without reading them. One machine per machine id. See `decisions/0012-remote-control-through-a-blind-relay.md`. Lives in `crates/relay/`. It exists twice, speaking one protocol: the Rust binary in `crates/relay/src/`, and the Cloudflare Worker in `crates/relay/worker/relay.js` that `<command> remote up` publishes on the owner's account.

**Machine id.** The first 16 bytes of the SHA-256 of the machine's public key, in hex: the name the relay knows the machine by. `tunnel::machine_id`.

**Remote book.** The machine's record for remote control, one private document (`remote/remote.json` in the data folder): its key, the relay's address, the paired devices and the pending invitations. `console::remote::Book`; the rules are in `Ledger`.

**Device.** A paired phone (or any browser), known by the public half of the key it made when it paired, and a name it gave (made unique by the machine). Revoking a device removes it from the book and cuts its open channels.

**Invitation / pairing link.** A one-time code the machine records as pending for ten minutes and prints as `https://<relay>/#pair=<machine key>.<code>`; the code rides in the fragment, which browsers never send. The phone that uses it first is paired and the invitation is gone. `tunnel::PairingLink`, `Book::invite`.

**Tunnel.** What runs inside a phone's channel once the Noise handshake is done: `Ask` from the phone (fetch, events, socket, send, close) and `Answer` from the machine (head, data, end), as JSON, sealed in pieces of at most one Noise message. `crates/tunnel/src/message.rs`, `transport.rs`; on the page `web/src/lib/tunnel/`.

## Names that collide

The audit listed these. Renamed on 2026-11-17: the background agent struct (`BackgroundAgent`, was `Task`), the worktree's cleanup (`WorktreeLease` in `agent_runtime/worktree_lease.rs`, was `Guard` in `guard.rs`), a hook's result (`HookOutcome`, was `hooks::Decision`), a memory's decided/ruled-out/watch-out note (`DecisionNote` in `knowledge/memory/decision_note.rs`, was `Decision`), what a hook says about the fallback chain (`FallbackChoice`, was `fallback::Verdict`), the router of the tools the loop handles itself (`agent/dispatch/in_loop.rs`, was `native.rs`), and the client (`app::Client`, was `Sdk`). What is left, and why it stays:

- "Task": the agent's to-do items (`TaskCreate`, `TaskList`) and background agents (`TaskOutput`, `TaskStop`). These are tool names the model sees, so they keep the names models know. The struct for one background agent of a run is `BackgroundAgent` in `crates/agent-engine/src/agent/subagents/background.rs`; what else a run holds (tool index, repeats, watches) is `ThisRun` in `crates/agent-engine/src/agent/run.rs`.
- "guard": `crates/agent-engine/src/guard/` is the bypass safety classifier, and `domain::permission::Guard` names what protects a path (outside the project, `.git/`, the app's own configuration). Both are the plain meaning of the word.
- "permission": `crates/domain/src/safety/permission/` (the policy engine and its verdict), `crates/agent-engine/src/agent/permission/` (the flow around it: hooks, the question, the bypass check), `crates/agent-engine/src/prompt/permissions.rs` (reading and writing rules in settings).
- "notice": an inbox notice (for the model), a harness notice (for the user) and a transcript notice entry; see "Notice (harness) vs inbox notice".
- "phase": only an engine phase of a run (see "Phase (engine)").
- "Conversations": the message delta recorded for the trace, and the stored sub-agent conversations.
- `crates/agent-engine/src/prompt/` in the engine holds project configuration (settings, rules, styles), not only prompts.
- `Decision` is the user's answer to an ask (`domain::Decision`, `crates/domain/src/run/approval.rs`); `PermissionDecision` is what a rule or a hook says (allow, ask, deny). `Verdict` is two types: the permission policy's (`domain::permission::Verdict`) and the verification judge's (`domain::Verdict`, `crates/domain/src/run/verification/mod.rs`). Both are re-exported by `app` and used by the CLI and the engine's tests, so a rename touches every layer; left for its own change.
- "Owner": the app's one user (the settings in their own folder are "the owner's", which a project layer cannot loosen); in `docs/feature-flags.md` and `docs/vision.md`, the project's author, who owns each experimental flag; and `LocalOwner`, the legacy tag left on disk from the removed owner concept, still hashed into session file names (`crates/domain/src/identity/legacy.rs`, `decisions/0008-single-user-local-product.md`).
- `Stop`: `platform::stop::Stop` is a run's cancellation (see "Stop (cancellation)", `crates/platform/src/stop.rs`); the engine's `Stop` (`crates/agent-engine/src/engine/stop.rs`) is how a run ends (completed, cancelled, failed, diagnosed, a model error), returned by a phase and turned into the run's last events. The hook event `Stop` is a third, the point where a run's answer ends.
- "Native" in the `native-sessions` folder means only "the engine built into the app" (the folder keeps its name on disk), and `Block::Native` is an item in a provider's own format, kept verbatim for that provider (its name is written into saved conversations).
