# Glossary

The project's own vocabulary. Code carries no comments (see `decisions/0010-comments-stay-out-of-code.md`), so a name is the only documentation next to the code and this file is where a name is explained. Paths are relative to the repository root and point at the main place a term lives today; the restructuring plan moves several of them.

The product is written as "the app", its binary as `<command>`, its project folder as `.<command>/` and its user folder as `~/.<command>/`.

## Runs and sessions

**Run.** One execution of the engine: one prompt (or one session command such as compact or rewind) from start to a terminal event. It has a `RunId`, runs on its own thread and ends with exactly one of `Completed`, `Failed`, `Cancelled`. Lives in `crates/agent-engine/src/engine/mod.rs`; the events are in `crates/domain/src/events.rs`.

**Turn.** One iteration of the agent loop inside a run: one model call plus the tool calls that reply asked for. A run has at most 200 turns. It does not mean "one user prompt and its answer"; that is a run. The TUI also has a `Turn` struct (`crates/cli/src/tui/turn.rs`) that holds the state of the run in progress, which is a different thing. Lives in `crates/agent-engine/src/agent/turn/`; the limit, `MAX_TURNS`, is in `crates/agent-engine/src/agent/mod.rs`.

**Turn state / transition.** The agent loop is a state machine. `TurnState` is what one run of the loop carries from step to step (the history, usage, fallbacks, reminders, cut-offs). `Next` is the step to take: ask the model, take its reply, run the tools it asked for, finish, or done. A transition is one such step: `Agent::turns` matches on `Next`, each handler returns the next one, and after every step that is not a model call `ThisRun::transition` hands the history to whoever keeps it. See `decisions/0002-agent-loop-state-machine.md`. `TurnState`, `Next` and `Agent::turns` live in `crates/agent-engine/src/agent/turn/mod.rs`; `ThisRun` in `crates/agent-engine/src/agent/run.rs`.

**Session.** A conversation kept on disk and continued across runs. It has a `SessionId` (a free string, a UUID when the engine creates it) and belongs to one project folder. Its conversation is read from disk at every run; what is costly to rebuild stays in its live session between runs (see `decisions/0001-long-lived-session.md`). On disk it is two append-only files in the data folder's `native-sessions/`: `<hash>.jsonl`, the conversation, written and synced at every transition of the turn, and `<hash>.trace.jsonl`, the trace; `<hash>` is a hash of the project path and the session id. Resuming reads the first only. Lives in `crates/agent-engine/src/sessions/mod.rs`.

**Live session.** What the engine keeps in memory for a session between its runs: its session cache, its MCP pool, and whether `SessionStart` has fired. It is entered when a run has loaded the session, so a chore (title) or a rewind enters none. At most eight are kept, least recently used out first; one in the middle of a run is never let go. It ends when it is pushed out or when the engine is dropped: `SessionEnd` fires then, if `SessionStart` did, and its MCP servers are terminated and waited for. Not to be confused with the TUI's fleet, which is what the terminal shows. `LiveSessions` and `LiveSession` live in `crates/agent-engine/src/engine/live/mod.rs`.

**Session cache.** The part of a live session that keeps the Brief (with its settings and hooks) and the script tools from one run to the next. Before each run a fingerprint of the files they are read from is taken: path, modification time, size and, for files up to 64 KiB, a hash of the content. The settings files and instruction files of the project, its parents and the owner's folder; the skills, commands, agents, rules, hooks, plugins, styles and tools folders; nested instruction files; the host's plugin and extra folders. The same fingerprint reuses what was loaded; any difference loads it again at that run's start, never in the middle of a run. What is not a file (environment, git state) is not watched. Lives in `crates/agent-engine/src/engine/live/cache.rs` and `sources.rs`.

**MCP pool.** The MCP servers a live session keeps connected across its runs. Each run asks the pool for the servers its settings, trust and approvals allow now; a server whose entry is unchanged and whose process is alive is reused, a new or changed entry is started, and one that is no longer wanted (removed, changed, approval revoked) is terminated and waited for. In-process servers (the host's own and script servers) are opened per run. Lives in `crates/agent-engine/src/mcp/pool.rs`.

**RunStart / RunEnd.** Hook events that fire once per run: `RunStart` after `SessionStart` (which fires only on a live session's first run) and before `UserPromptSubmit`, with the same input as `SessionStart` and its context added to the prompt; `RunEnd` when the run closes, whatever its outcome, before the conversation is saved. They took over what `SessionStart` and `SessionEnd` did before the live session. Fired from `crates/agent-engine/src/engine/live/events.rs` and `crates/agent-engine/src/engine/phases/close.rs`.

**Transition.** A step of the turn's state machine after which the conversation is on disk: before a model call, after its reply is recorded, after a batch of tool results. A process that dies loses at most what happened since the last one; a tool call left without its result is closed as interrupted on resume. See `decisions/0002-agent-loop-state-machine.md`. Lives in `crates/agent-engine/src/agent/turn/mod.rs`.

**Amendment.** A conversation log entry, written as `truncated` with `amended: true`, that cuts the kept conversation back to the first message that changed before the new version of it is appended; a reminder added to tool results that were already saved is the usual cause. It is not a rewind and the trace does not show it as one. Lives in `crates/agent-engine/src/sessions/log.rs`.

**Job.** The object that prepares and drives one run. It is not a queue entry and there is no scheduler; "job" and "run" have the same lifetime. Lives in `crates/agent-engine/src/engine/job.rs`.

**Phase (engine).** One of the eight typed steps `Job::phases` runs in order for a run: `load_session`, `brief`, `equip`, `apply_policy`, `prepare_runtime`, `open`, `drive`, `close`. Each takes what the one before produced; a phase that ends the run early returns a `Stop`, which is turned into the run's last events in one place. A phase is not a turn (a step of the agent loop, inside `drive`) and not one of the plan's eleven phases in `architecture.md`. The list is in `crates/agent-engine/src/engine/job.rs`, each phase in `crates/agent-engine/src/engine/phases/`, `Stop` in `crates/agent-engine/src/engine/stop.rs`.

**Run gate.** The point every engine event passes through on its way out. It lets exactly one terminal event through and nothing after it, so a caller can rely on a run ending once. Lives in `crates/agent-engine/src/boundary/gate.rs`.

**Brief.** What the engine gathers from a folder before a run: plugins, settings, skills, agents, rules, instruction files and a git snapshot. It is kept in the session cache and loaded again only when a file it was read from changed, so a `Brief` hook runs at a live session's first run and after such a change, not at every run. `Brief` is also the name of a hook event that may rewrite that result, and `MemoryBrief` (`crates/domain/src/memory/brief.rs`) is the unrelated piece of memory that goes into a request. Lives in `crates/agent-engine/src/brief.rs`.

**Checkpoint / rewind.** A checkpoint is taken once per prompt and keeps the previous content of every file the run edited, with the position in the conversation. Rewind restores those files and cuts the conversation back to that prompt (the cut is skipped if a compaction changed the history since). Branch starts a new conversation from before a prompt. A session keeps the files of its newest 50 checkpoints and at most 64 MiB of them, in `native-sessions/checkpoints-<hash>.json`; an older checkpoint keeps its place in the list but not its files, so it can be branched from and not rewound to. Lives in `crates/agent-engine/src/checkpoints.rs`. The `Checkpoint` in `crates/cli/src/tui/rewind.rs` is the TUI's row for one of them in the rewind list.

**Upkeep / compaction.** Upkeep is the module that keeps a conversation inside the model's context window: it measures usage, replaces old tool results with a marker, and compacts. Compaction asks the model to summarise the older part of the history and keeps the most recent tail verbatim. It runs automatically near the limit, after a "too long" error from the provider, or on `/compact`. Lives in `crates/agent-engine/src/upkeep/`.

**Chore.** An auxiliary model call made around a run, not part of the conversation: session title, next-prompt suggestion, recap on resume, side question, heads-up, branch name, lesson. The TUI starts several after each completed run, so they cost model calls the user does not see. A chore is not a background job and is not recorded in the session catalog. Lives in `crates/agent-engine/src/chores/mod.rs`; triggered from `crates/cli/src/tui/chores.rs`.

**Steer.** Text the user sends while a run is in progress. It is queued and delivered to the model with the next tool results or at the end of the turn; "unsteer" takes back what was not delivered yet. It does not interrupt the run. Lives in `crates/agent-engine/src/control.rs`.

**Ask.** A question the engine puts to the user in the middle of a run, which waits for the answer: a permission request, a set of questions, or a plan approval. The type is `AgentAsk`; the answer is a `Decision`. "Ask" is also the name of a permission mode and of a rule kind. Lives in `crates/domain/src/approval.rs`.

**Fleet.** The sessions that are live in one terminal process, shown by `/fleet`. It is a list of sessions, not a group of agents or machines. Lives in `crates/cli/src/tui/fleet/mod.rs`.

**Parked session.** A live session in the fleet that is not the one on screen. Its state is held aside and swapped into the TUI's `App` when one of its events arrives. Lives in `crates/cli/src/tui/fleet/parked.rs`.

**Carried / run watch.** What a client's session carries from one run to the next: the session id, the permission mode, what was spent against the budget, the verification criteria, the corrections a lesson may be drawn from and a pending fork. `Carried::observe` applies a run's events to it, and `Touches` says what a run of a given `SessionCommand` may change: a prompt changes everything, a session command (compact, rewind, branch, measure) only the session id, a chore nothing but the spending. `RunWatch` is the per-run part, which also follows the plan being written (`PlanWatch`: the plan presented for approval, else what a planning run said). The rules live in `crates/domain/src/session_run.rs` and `crates/domain/src/verification/plan_watch.rs`; the client holds the lock in `crates/app/src/client/session.rs` and `crates/app/src/client/run.rs`.

**Peer.** Another client in the same process, registered under a name built from its folder and client number. The `ListSessions` tool lists peers and `SendMessage` can address one. Lives in `crates/agent-engine/src/tools/peers.rs`.

## Permissions

**Permission mode.** How much the agent may do without asking: `Ask`, `AcceptEdits` (the default, shown as "edits"), `Plan` (no edits, no execution), `Bypass`. There is no fifth "auto" mode: the safety classifier that reviews actions in bypass and the automatic model picker are separate mechanisms. Lives in `crates/domain/src/approval.rs`.

**Effect.** What one tool call will do, declared by the tool in Rust from its input (`Tool::effects`): read a path or a folder tree, write a path, execute a parsed shell command, reach a network host, spawn work (a sub-agent, a background shell, a schedule, a watch), cancel work (its own or not), notify the user, message another session, read an MCP resource, call an MCP server, or the coarse class a user script tool declares (`Declared::Edits`, `Declared::Executes`). A call with no effects only reads state the agent owns. Paths carry both the path as written and where it really leads (symlinks resolved). Lives in `crates/domain/src/permission/effect.rs`. There is no per-tool `access` class any more; `Access` in `crates/domain/src/model.rs` is unrelated: it is how a provider is signed in to (key, browser, code).

**Policy engine / verdict.** `PolicyEngine::decide` judges a call (tool name, subject, effects) in a `PolicyContext` (mode capped by a sub-agent's ceiling, project roots and added folders, protected locations `.git/` and the app's own configuration folder, allow/ask/deny rules, remembered answers, sandbox, whether the user can be asked) and returns a `Verdict`: `Allow`, `Ask { reason, rememberable, rule }` or `Deny(reason)`. The reason says why it asks (the mode, a rule, a hook, reading outside, a guarded write, a risky command, an address, leaving the sandbox, a package concern, installing a language server). An `Effect::Install` (a language server the `LSP` call would install first) is asked in every mode, bypass included, and refused while planning, unless a rule naming it (`LSP(install:<server>)`, never a bare `LSP`) allows or denies it; where nobody can be asked the refusal names that rule. Hooks, the bypass safety classifier and the question to the user are orchestration around it in `crates/agent-engine/src/agent/permission/`. Lives in `crates/domain/src/permission/`; see `decisions/0003-effects-based-permission-policy.md`.

**Shell command / opaque.** A Bash command line parsed by `domain::shell` into every simple command it runs, including those inside control structures, function bodies, subshells, command and process substitutions and `find -exec`. A line the parser cannot follow with confidence is opaque: never read-only, never allowed by a rule with a specifier, and asked about when a deny or ask rule with a specifier exists. Lives in `crates/domain/src/shell/`.

**Trust (workspace trust).** The user's stored answer to "may this project folder run code and grant itself permissions?". It is `Trust::Trusted` or `Trust::Untrusted`, kept per trust root (the nearest ancestor containing `.git`, else the folder itself; never the home folder or a file-system root) in `users/local/trusted-folders.json`, and handed to the engine by the handler as `Extensions.trust`. In an untrusted folder the engine's `Gate` skips project hooks, scripts, MCP servers, declared providers, language-server commands and the owner reading of `settings.local.json`; instruction files and deny or ask rules still apply. It is not a per-item approval (a trusted project's MCP server still waits for its own), not the `trusted` field of a found skill or script tool (which says whether a script is the owner's or the project's, for script access), and not "untrusted content" (text the model read). A `Contributions` is the typed list of what a folder brings that trust would enable; a `TrustReport` is the state plus that list. See `decisions/0004-workspace-trust.md`. The rule is in `crates/domain/src/trust/`, the gate and the scan in `crates/agent-engine/src/trust/`, the store in `crates/app/src/trust.rs`.

**Sandbox / confinement.** The `experimental-sandbox` feature: shell commands the agent runs (Bash, Monitor, a script's `ctx.exec`, a script MCP server's `ctx.exec`, command hooks) and stdio MCP servers start confined so they write only in the project, added folders, the temporary folders, package caches and `sandbox.allowWrite`. A `Confinement` is that list for one run (`crates/domain/src/sandbox.rs`, `crates/platform/src/sandbox.rs`); it is applied by `sandbox-exec` on macOS and by Landlock on Linux (`crates/platform/src/linux/landlock.rs`). `platform::sandbox::support()` says whether this system can apply it and, when it cannot, why. Where it cannot, the run says so once (a harness notice); with `sandbox.required` (true by default on Linux and macOS, `REQUIRED_BY_DEFAULT`; only the owner turns it off) the policy engine refuses every confined command (`sandbox_missing` in `PolicyContext`) and stdio MCP servers do not start, otherwise both run unconfined. A stdio MCP server's own entry in `mcp.json` may add folders (`sandbox.writable`), keep it off the network (`sandbox.network: false`, network is on by default for servers) or, from the owner's file only, opt out (`"sandbox": false`); that entry is a `ServerSandbox`, settled per run into a `StdioSandbox` (`Confined`, `Unconfined` or `Refused`) in `crates/agent-engine/src/mcp/stdio_sandbox.rs`. It is not workspace trust and not the script runtime's own limits.

**Fence (untrusted content).** The `<untrusted-content>` wrapper put around text the model reads that someone other than the user wrote: a fetched page (before the reader model sees it) and the result of an MCP tool or resource (before the main model sees it). It ends with a line saying where the text came from and that it is data, not instructions; any opening or closing tag inside the text, in any letter case, is escaped so it cannot close the fence. Lives in `crates/domain/src/untrusted.rs`.

**Permission rule.** An allow, ask or deny line, written `Tool` or `Tool(specifier)`. Deny wins over ask, ask over allow; with no rule the mode decides. Lives in `crates/domain/src/permission_rules/mod.rs`.

## Models

**Provider vs vendor.** A provider is a way to reach models: an endpoint plus an authentication method (an API key, a sign-in). A vendor is a model family: its prices, aliases and reasoning rules. The same vendor's models can be reached through more than one provider. The `Provider` trait is in `crates/llm-providers/src/lib.rs`, one folder per provider is in `crates/llm-providers/src/providers/`, and `Vendor` is in `crates/llm-providers/src/vendor.rs`.

**Wire.** The request and streaming format of a model API: `chat`, `messages`, `responses`. A provider names the wire each of its models speaks. It is not the protocol between the terminal and the backend. Lives in `crates/llm-providers/src/model/wires/`.

**Model roles: small model, advisor, judge.** A session can assign different models to different jobs. The small model does cheap auxiliary work, such as reading a fetched web page before the main model sees it. The advisor is a second model the agent can consult through the `Advisor` tool. The judge is the model that decides whether a run met its verification criteria. Other roles are plan, explore and review. Roles are in `crates/domain/src/model_roles/mod.rs` and resolved in `crates/agent-engine/src/engine/roles.rs`.

**Verification.** Criteria that a run's result is judged against when it finishes, taken from the user, from the plan, or from the project's `verification.md`. A failed verdict sends the agent back to work, up to three attempts; nothing is verified in plan mode. It is not the `verify` skill and not the repository's own test gate. Lives in `crates/domain/src/verification/mod.rs`.

## Configuration

**Workspace vs project.** `Workspace` is an engine type: the per-run context handed to every tool (folders, policy, models, services). It is not a folder and not the Cargo workspace. The project is the folder the user works in, with the `.<command>/` folders of it and its ancestors. "Workspace trust" in `decisions/0004-workspace-trust.md` is about the project folder (see **Trust**). `Workspace` lives in `crates/agent-engine/src/tools/workspace/mod.rs`.

**Settings vs UI state.** Settings are the configuration files a user or a project writes: `~/.<command>/settings.json`, `<project>/.<command>/settings.json` and `settings.local.json` (rules, hooks, flags, model roles). They are read by `crates/agent-engine/src/prompt/settings.rs`. UI state is what the TUI remembers for itself (model, mode, prompt history, last session per folder), stored in the data folder. The code calls both "settings"; the UI state is written by `crates/cli/src/tui/settings.rs` through `crates/app/src/settings.rs`, as a list of `SettingsChange` applied under the file's lock rather than as a whole document.

**Document (persistence helper).** A JSON (or text) file that is read, changed and replaced whole under one policy: cross-process lock with a bounded wait, atomic replace, nothing written when nothing changed, and a file that does not parse set aside as `<name>.corrupt-<epoch seconds>` (program-owned) or reported and left alone (hand-edited). Every JSON store of the application goes through it (settings, UI state, provider accounts, the vault's entries, `mcp.json`); the session catalog and project memory are rows in the SQLite database `app.db` instead (`crates/app/src/db/`), and a session's log is append-only. See `decisions/0006-one-persistence-pattern.md`. It is not a file the agent edits for the user. Lives in `crates/platform/src/store/mod.rs`.

**Data root.** Where one instance of the application keeps everything it owns: the folders for UI state, provider accounts, the code-map cache, session logs, language servers, the vault and `app.db`. `DataRoot::system()` is the user's real data folder, `DataRoot::under(folder)` puts all of it under one folder (`Sdk::builder().data_dir`, used by tests), and `DataRoot::in_memory()` keeps nothing on the machine. It also opens the stores; when `app.db` cannot be opened it falls back to stores that last as long as the process and records why, which reaches the user once as a harness notice. It is not the project folder and not `~/.<command>/`. Lives in `crates/app/src/data_root.rs`; the recorded reason is a `Degraded` (`crates/app/src/degraded.rs`).

**Feature vs feature flag.** A feature is a folder of code that plugs into a host: `crates/app/src/features/<name>/` on the backend and `crates/cli/src/tui/features/<name>/` in the TUI. A feature flag is a named on/off switch in the settings' `features` key, defined in `crates/domain/src/features.rs`; every flag is on unless turned off, except the opt-in ones (`experimental-code-mode-only`), which are off until the owner turns them on. A backend feature is turned off only through its switch, the flag `FeatureName::switch` names for it (`crates/app/src/api/features/mod.rs`; the flags that exist only for that are in `crates/domain/src/features/backend.rs`); `flags`, `sessions`, `shell` and `workspace` have none and are always on. A name that is not a known flag switches nothing. A Cargo feature is a third, unrelated thing.

**Content.** The `content/` folder: prompts, tool descriptions, hooks, output styles, built-in agents and skills, written in JavaScript and Markdown and embedded in the binary at build time. A file with the same path under `~/.<command>/` overrides the embedded one. It does not mean message content. The `content` crate is in `crates/content/src/lib.rs`; the JavaScript contract is `content/types.d.ts`.

**Hook events.** The points where user code can observe or change a run. There are nineteen: `Brief`; `SessionStart`, `SessionEnd` (once per live session), `RunStart`, `RunEnd` (once per run), `UserPromptSubmit`; `ModelRequest`, `ModelResponse`, `ModelError`; `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`; `PreCompact`, `PostCompact`; `Stop`, `SubagentStart`, `SubagentStop`; `Notification`. A hook is a shell command, an HTTP call, a script, a model prompt or a sub-agent. The list is in `crates/agent-engine/src/hooks/validate.rs`.

**Script tool.** A tool a user or project writes in JavaScript under `.<command>/tools/`, run in the embedded QuickJS runtime. It is distinct from the `content/tools/<Name>.js` files, which describe and wrap the built-in Rust tools. Lives in `crates/agent-engine/src/tools/script_tool.rs`; the runtime is `crates/script/src/lib.rs`.

**Capability (script) / host call / host judge.** A host function a script must declare before it may call it: `readFile`, `writeFile`, `exec`, `fetch` (`Capability`, `Capabilities` in `crates/agent-engine/src/tools/script_tool.rs`). Where it is declared depends on the kind (`Declaration`): a script tool in `spec.capabilities`, a hook or skill script in `export const capabilities`, a script MCP server in its default export's `capabilities`; a declared provider and a prompt have none (`Declaration::Nowhere`). An undeclared call fails naming the missing entry and where it goes; a declared one must also be granted by the `scripts.*` settings (`ScriptAccess`), and is then judged as the tool that does the same thing (`Read`, `Write`, `Bash`, `WebFetch`) by the policy engine, so it can ask, be ruled or be refused. A script tool's judged call is a `HostCall` (`crates/agent-engine/src/agent/scripts/host_calls.rs`), asked through the agent like any tool call. Hooks, skill scripts and script MCP servers are judged by the run's `HostJudge` (`crates/agent-engine/src/tools/host_judge.rs`), which the engine puts in `Services.judge`: it reads the live mode and remembered answers from the run's `Control`, the rules, bounds and sandbox state from `Grounds`, and asks the user through the run's event gate; without a run (or with prompts off) a call that would ask is refused and the refusal names the rule that would allow it. It is unrelated to the `access` field, which is the coarse class of the tool call itself, and to an MCP server's "capabilities" in its handshake.

**Script limits.** Every script run has a memory limit (64 MiB), a stack limit (1 MiB) and a time limit: a hook, a prompt or a skill script has a wall-clock limit (`script::Limit::Wall`), and a script tool or a script MCP server a budget of running time that does not count time spent waiting on the app, such as a question to the user (`script::Limit::Busy`, `script::MOST_BUSY`). Lives in `crates/script/src/lib.rs`.

**Input check.** Before a tool call is judged or run, its input is validated against the JSON schema the model was given for that tool (a built-in tool's `content/tools/<Name>.js`, an MCP server's `inputSchema`, a script tool's `spec.input`); an invalid input is returned to the model as an error naming the field, and the tool's effects are never computed. An optional field sent as `null` counts as left out. Schemas are compiled once and kept. Lives in `crates/agent-engine/src/tools/checked.rs`.

**Code mode / REPL.** The `REPL` tool, behind the `experimental-code-mode` flag: the model writes JavaScript in which every other tool it was offered is an async function, and only what the script returns or passes to `self.log` reaches the model. Each call inside a script is an ordinary tool call, with its hooks, rules and permission asks. With the opt-in `experimental-code-mode-only` flag, REPL is the only tool besides the turn-level ones and every other tool is declared inside its description. The JavaScript context persists per session and agent, so what one script declares the next can read; it is a `script::session::Session`, distinct from the conversation **Session** above and from the one-shot runs of script tools. See `decisions/0011-code-mode.md`. The tool is in `crates/agent-engine/src/tools/repl.rs` and `crates/agent-engine/src/agent/repl.rs`, the context in `crates/script/src/session.rs`, the output rules in `crates/domain/src/code_mode.rs`.

**Skill.** A folder with a `SKILL.md` (front matter plus instructions, optionally supporting files) that the model loads through the `Skill` tool or the user runs as `/name`. Built-in skills are in `content/skills/`. Lives in `crates/agent-engine/src/tools/skill.rs`.

**Plugin.** A git checkout under `~/.<command>/plugins/<name>/` that contributes hooks, MCP servers and language-server definitions. Lives in `crates/agent-engine/src/plugins.rs`.

**Worktree.** A git worktree the engine creates under `<repository>/.<command>/worktrees/` so a sub-agent or a session can work in isolation. It is removed at the end if nothing changed and kept otherwise. Lives in `crates/agent-engine/src/agent_runtime/mod.rs`.

**Child.** A process the application started and answers for, held as a `platform::child::Child`: a Bash shell, a monitor, an MCP stdio server, a language server, a hook command, a git helper. It runs in its own process group, is stopped politely before it is killed, is always waited for, and can keep the end of what it wrote to its error stream. It is not a sub-agent (a child run of the agent loop, which is a thread, not a process) and not the web terminal's pseudo-terminal process. "Grace" is how long a child is given between the polite stop and the kill; "reaped" means it has been waited for, after which nothing is signalled. See "Child processes" in `architecture.md`. Lives in `crates/platform/src/child.rs`.

## Memory and messages to the agent

**Memory kinds.** A project memory entry is `Episodic`, `Semantic` or `Procedural`. Only episodic entries decay with time; an entry given without a kind is stored as semantic. Lives in `crates/domain/src/memory/mod.rs`. Three different stores are all called memory: project memory (per project, in the data folder), team memory (Markdown files in `<project>/.<command>/memory/`) and agent memory (a `MEMORY.md` per custom agent).

**Inbox / inbox notice / channel.** The inbox is a queue of short messages waiting to be shown to the agent during a run. An inbox notice (`domain::inbox::Notice`, a source and a text) is one such message, for example a line from a monitored background command. A channel is an MCP server that stays open for the session and pushes notices into the inbox. Inbox notices are treated as untrusted data and are delivered to the model, as events of the run or as a turn of their own when the session is idle. The rules are in `crates/domain/src/inbox.rs`, the queue in `crates/agent-engine/src/tools/inbox.rs`, channels in `crates/agent-engine/src/mcp/channel.rs`. The in-process message channels between threads are unrelated.

**Notice (harness) vs inbox notice.** A harness notice is something the application itself has to tell the user: keys cannot be kept on this machine, the session list and memory could not be opened. It is shown in the transcript as a notice (or printed to the error stream with `--print`), said once per process, and never sent to the model. Both kinds answer the same command, `ClientCommand::TakeNotices { for_agent }`, in the two typed fields of `Notices`: `for_user` (harness) and `for_agent` (inbox, taken only when asked for). The type is in `crates/app/src/api/event.rs`, the handler in `crates/app/src/handler/mod.rs`, the TUI side in `crates/cli/src/tui/notices.rs`. The transcript's own "notice" entry (`Transcript::notice`) is just a line the TUI shows; a harness notice becomes one.

## Client and handler

**Request id / reply / unsolicited event.** Every `ClientCommand` the client sends is wrapped in an `Envelope` with a `RequestId`, a number the client counts up. A `Reply` is a `ServerEvent::Reply` carrying the id of the request it answers; a request gets one terminal reply, after any number of non-terminal ones (a sign-in's "authorize at" step). A command whose handler panics is answered `internal error while handling <command>`. An unsolicited event (`ServerEvent::Unsolicited`) answers no request: the handler tells the client something that happened by itself, such as memory applied after a run or a model catalog that failed to load; the client keeps the latest 256 until they are read. Run events (`ServerEvent::Run`) are the third kind and are routed by `RunId`. The types are in `crates/app/src/api/` (`envelope.rs`, `command.rs`, `event.rs`), the waiting and routing in `crates/app/src/client/dispatch.rs`, the sending side in `crates/app/src/handler/outbox.rs`.

## Observability

**Trace / lane / span.** The trace is the record of what happened in a session's runs: prompts, events, model calls. It is written to the session's own trace file, `native-sessions/<hash>.trace.jsonl`, as the run proceeds (buffered, flushed at each transition; set aside as `<hash>.trace.1.jsonl` past 64 MiB), read back merged with the conversation log by sequence number, and projected three ways. A session written before the split has its trace inside `<hash>.jsonl`, which is still read. The first projection is a `Trace` holding a `Lane` of steps, each step a set of timed nodes. The second is a list of runs, each a tree of `Span`s (run, model call, tool, agent, task, eval, wait, event); this is what the trace page draws. The third is the report with totals and insights. Lives in `crates/domain/src/trace/`.

## Names that collide

The audit lists these; until they are renamed, check which one a file means.

- "Task": the agent's to-do items (`TaskCreate`, `TaskList`), background agents (`TaskOutput`, `TaskStop`), and a `Task` struct, one background agent of a run, in `crates/agent-engine/src/agent/subagents/background.rs`. What else a run holds (tool index, repeats, watches) is `ThisRun` in `crates/agent-engine/src/agent/run.rs`.
- "guard": `crates/agent-engine/src/guard/` is the bypass safety classifier; `crates/agent-engine/src/agent_runtime/guard.rs` cleans up a worktree.
- "permission": `crates/domain/src/permission/` (the policy engine and its verdict), `crates/agent-engine/src/agent/permission/` (the flow around it: hooks, the question, the bypass check), `crates/agent-engine/src/prompt/permissions.rs` (reading and writing rules in settings).
- "notice": an inbox notice (for the model), a harness notice (for the user) and a transcript notice entry; see "Notice (harness) vs inbox notice".
- "phase": an engine phase of a run, and a phase of the restructuring plan.
- "Conversations": the message delta recorded for the trace, and the stored sub-agent conversations.
- `crates/agent-engine/src/prompt/` in the engine holds project configuration (settings, rules, styles), not only prompts.
- `Decision` and `Verdict` each name more than one type across `domain` and the engine.
- "Native" in `NativeEngine` and `native-sessions` means only "the engine built into the app".
